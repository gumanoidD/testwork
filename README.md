# Telegram Web Scraper & Analytics API

Сервіс для інкрементального збору публічних Telegram-каналів через веб-версію
(`t.me/s/<channel>`) та надання аналітики через REST API.

## ⚡ Швидкий запуск (до 5 хвилин)

Створити файл конфігурації:
```
cp .env.example .env
```

Запустити через Docker Compose:
```
docker compose up --build
```

Контейнер сам одразу піднімає фоновий збір (кожні `FETCH_INTERVAL` секунд), тож
перші дані з'являться протягом хвилини після старту навіть без ручного виклику CLI.

Перевірка роботи:
- Swagger UI (API Docs): http://localhost:8000/docs
- Healthcheck: http://localhost:8000/healthz
- Фронтенд: http://localhost:8000/

## 🛠️ CLI команди (ручний збір)

Всередині контейнера:
```
docker compose exec app python -m app.cli collect
docker compose exec app python -m app.cli collect --backfill
```

Локально (без Docker, з кореня проєкту, після `pip install -r requirements.txt`):
```
python -m app.cli collect
python -m app.cli collect --backfill
```

## 📊 Формула топ-постів (`GET /channels/{name}/top`)

Ендпоїнт визначає найпопулярніші пости каналу за останні N днів (`days`, за
замовчуванням 7):

1. Береться вибірка всіх постів каналу за вказаний період.
2. Обчислюється медіана переглядів (`M`) серед постів вибірки.
3. Для кожного поста рахується `score = views / M`.
4. Пости сортуються за спаданням `score`.

Медіана, а не абсолютні перегляди, використана свідомо — щоб маленький канал не
губився на фоні великого: у обох випадках "вірусний" пост — це той, що суттєво
відхиляється від типового для свого ж каналу, а не для Telegram в цілому.

## 📈 Динаміка переглядів

При кожному запуску скрапера поточна кількість переглядів поста записується в
окрему таблицю `post_metrics` з часовою міткою `fetched_at`, замість
перезапису значення в `posts`. Це дозволяє зберігати часовий ряд і бачити,
як швидко пост набирає перегляди між заходами збирача, а не лише останнє
значення. Деталі рішення — у `docs/adr/001-metrics-storage.md`.

## ⚠️ Обмеження рішення

- Інкрементальний `collect` (без `--backfill`) читає лише першу сторінку
  `t.me/s/<channel>` (~20 останніх постів). Якщо канал постить частіше, ніж
  запускається збір, частина постів між двома запусками може бути пропущена.
  Це свідомий компроміс: припускається, що фоновий цикл (`FETCH_INTERVAL`,
  за замовчуванням 300с) запускається достатньо часто.
- Ретраїв — обмежена кількість (3 спроби з backoff) на рівні одного HTTP-запиту;
  немає окремого rate-limit throttling понад невелику паузу між сторінками
  `--backfill`.
- Немає дедуплікації "та сама новина в різних каналах" — це опціональна LLM-частина
  ТЗ, яку в цій версії не реалізовано (обрано фронт замість неї).
- Парсер завʼязаний на поточну розмітку `t.me/s/`; при зміні верстки Telegram
  парсинг зламається без явного попередження (лог warning при 0 знайдених постах).

## 🧪 Тести

```
python -m pytest
```

Без мережі: парсинг HTML з фікстур (`tests/fixtures/`), ідемпотентність
повторного `collect`, арифметика медіани в `/channels/{name}/top` через
`TestClient` (реальний виклик ендпоінта, а не переобчислення формули окремо).
